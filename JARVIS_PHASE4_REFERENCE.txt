  WHAT PHASE 4 ADDS (OVER PHASE 3)
--------------------------------------------------------------------------------

  Phase 3 handled one action per command:
    "open chrome"      -> opens Chrome (1 action)
    "play kesariya"    -> plays song   (1 action)

  Phase 4 handles multi-step routines triggered by one sentence:
    "start coding session"  -> opens Chrome + GitHub + focus music (3 actions)
    "morning routine"       -> opens Gmail + searches news + plays music (3 actions)
    "i want to chill"       -> opens YouTube + plays lofi music (2 actions)
    "i want to study"       -> opens Wikipedia + StackOverflow + study music (3 actions)

  The AI detects WORKFLOW intent and the Workflow Engine executes all steps.
  Each step reuses existing action handlers -- zero new action code written.

--------------------------------------------------------------------------------
  THE PIPELINE: PHASE 3 vs PHASE 4
--------------------------------------------------------------------------------

  PHASE 3 PIPELINE (single-action):
    raw input
      -> [Input Handler]      normalize text
      -> [AI Parser]          classify intent + extract entity
      -> [Action Executor]    run ONE action
      -> response

  PHASE 4 PIPELINE (workflow path):
    raw input
      -> [Input Handler]      normalize text
      -> [AI Parser]          detects WORKFLOW intent
                              returns: { workflow_name: "coding session" }
      -> [Action Executor]    sees INTENT_WORKFLOW
      -> [Workflow Engine]    looks up "coding session" in config/workflows.py
                              executes Step 1: Open Chrome
                              executes Step 2: Open GitHub
                              executes Step 3: Play focus music
      -> combined response

  PHASE 4 PIPELINE (single-action path -- unchanged):
    Same as Phase 3. If AI returns PLAY_MEDIA, OPEN_APP etc.,
    the executor handles it exactly as before.

  KEY DESIGN POINT:
    The Workflow Engine calls executor.execute() for EACH step.
    This means ALL existing action handlers (media, browser, apps) are
    reused without any modification. Zero code duplication.

  [4] actions/workflow_engine.py  (NEW)
  ---------------------------------------
  What it is:
    The engine that resolves and executes workflows step by step.

  How it works:
    1. Receives workflow_name (may be fuzzy/informal)
    2. Resolves to canonical name via _resolve_workflow_name()
    3. Looks up steps in WORKFLOWS dict
    4. For each step:
       a. Prints step label to terminal
       b. Creates a mini Command object with the step's intent + entities
       c. Calls executor.execute(mini_cmd)
       d. Prints [OK] or [!] result
    5. Returns (all_ok, summary_message)

  _resolve_workflow_name() -- 4-tier fuzzy matching:
    Tier 1: Exact match in WORKFLOWS dict
    Tier 2: Alias lookup in WORKFLOW_ALIASES
    Tier 3: Partial starts-with match in WORKFLOWS keys
    Tier 4: Substring match in WORKFLOWS keys

  Why the engine receives the executor (not imports it):
    Dependency injection. Same pattern as the pipeline.
    Makes the engine testable and decoupled.
    The engine does NOT know what actions exist -- it just delegates.

  Terminal output during workflow:
    [Workflow] Starting 'coding session' (3 steps)
    [Workflow] Step 1/3: Opening Chrome...
    [Workflow]   [OK] Opening Chrome...
    [Workflow] Step 2/3: Navigating to GitHub...
    [Workflow]   [OK] Opening github in your browser...
    [Workflow] Step 3/3: Playing focus music...
    [Workflow]   [OK] Playing 'lofi hip hop focus music' on YouTube...

  Works correctly: YES
  Tests passed:   8/8


  [5] actions/executor.py  (UPDATED)
  -------------------------------------
  What changed:
    Added INTENT_WORKFLOW import.
    Added WORKFLOW dispatch BEFORE the dispatch table.
    For WORKFLOW: calls workflow_engine.run_workflow(name, executor=self)
    Passes self so the engine can call executor.execute() for each step.

  Why WORKFLOW is handled before the dispatch table:
    It needs special treatment (receives the executor itself).
    The dispatch table maps to simple (value) -> (bool, str) functions.
    WORKFLOW doesn't fit that pattern.

--------------------------------------------------------------------------------
  FULL PIPELINE FLOW EXAMPLE
--------------------------------------------------------------------------------

  User types: "prepare me to work"

  Stage 1 -- Input Handler
    Output: "prepare me to work"

  Stage 2 -- AI Parser
    Sends to Groq API.
    LLM returns:
      { "intent": "WORKFLOW",
        "entities": { "workflow_name": "coding session" },
        "confidence": "high" }
    cmd.intent   = "WORKFLOW"
    cmd.entities = { "workflow_name": "coding session" }

  Stage 3 -- Action Executor
    Sees INTENT_WORKFLOW.
    Calls workflow_engine.run_workflow("coding session", executor=self)

  Inside Workflow Engine:
    _resolve_workflow_name("coding session"):
      Tier 1 exact match -> "coding session" found in WORKFLOWS
    steps = WORKFLOWS["coding session"]  (3 steps)

    Step 1: mini_cmd.intent="OPEN_APP", entities={"app_name":"chrome"}
      executor.execute(mini_cmd) -> apps.open_app("chrome") -> [OK]

    Step 2: mini_cmd.intent="OPEN_WEBSITE", entities={"website":"github"}
      executor.execute(mini_cmd) -> browser.open_website("github") -> [OK]

    Step 3: mini_cmd.intent="PLAY_MEDIA", entities={"song_name":"lofi hip hop..."}
      executor.execute(mini_cmd) -> media.play_media("lofi hip hop...") -> [OK]

    Returns: (True, "Workflow 'coding session' complete! (3/3 steps succeeded)")

  Final output to user:
    [OK] JARVIS: Workflow 'coding session' complete! (3/3 steps succeeded)

--------------------------------------------------------------------------------
  KNOWN LIMITATIONS (Phase 4)
--------------------------------------------------------------------------------

  - Workflow steps execute sequentially (one after another).
    Parallel execution (all at once) comes in a future phase.

  - If one step fails, remaining steps still execute.
    There is no "abort on failure" behavior yet.

  - Workflow names must be in config/workflows.py.
    JARVIS cannot create new workflows dynamically yet (Phase 5).

  - AI may occasionally map a phrase to the wrong workflow.
    Example: "let's work" might map to coding session or study session.
    Fix: add more explicit aliases in WORKFLOW_ALIASES.
